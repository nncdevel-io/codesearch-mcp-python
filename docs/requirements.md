# Code Search MCP Server — 要件書

本書は、Git リポジトリ上のソースコードを検索するための
Model Context Protocol (MCP) サーバーの要件を定義する。

LangChain Chatbot ([chat.langchain.com](https://chat.langchain.com))
と同等のチャットアプリケーションを支える「コードベース検索」基盤
として位置付ける。

## 1. 目的と背景

### 1.1 目的

チャットアプリケーションのエージェントから利用される、Git 管理
されたソースコードに対する検索基盤を MCP サーバーとして提供する。

エージェントは本サーバーが公開するツールを通じて、ソースコード
全体に対するパターン検索、ファイル名による検索、ファイル内容の
読み取りを行い、ユーザーへの回答に必要な実装上の根拠
(ファイルパス、行番号、Git URL) を取得する。

### 1.2 背景

LangChain のチャットボット再構築事例
([Why We Rebuilt LangChain's Chatbot](https://www.langchain.com/blog/rebuilding-chat-langchain))
において、構造化されたコードベースに対する検索手段として
ベクトル検索 (チャンク化 + 埋め込み + 類似度検索) は次の問題を
抱えることが示されている。

- チャンク化により関数・クラス境界が断裂し、文脈が失われる
- リポジトリ更新のたびに再インデックスが必要になり運用負荷が高い
- 引用が曖昧になり、ユーザーが実装根拠を検証できない

LangChain は最終的にベクトル検索を捨て、パターンマッチング、
ファイル探索、行番号付きファイル読み取りという「人間が
Claude Code でコードを追う手順」を再現するアプローチに切り替えた。

本サーバーはこの方針を踏襲する。具体的なツール設計は、Claude Code
が組み込みで提供する `Grep`、`Glob`、`Read` の各ツール仕様
([Claude Code Tools Reference](https://docs.claude.com/en/docs/claude-code/overview))
を参考にしつつ、複数リポジトリを扱う MCP サーバーとしての要件に
合わせて調整する。

Claude Code が想定するローカル開発作業と異なり、本サーバーは
エージェントが初見のリポジトリを相手にする場面が多い。
そのため Claude Code には存在しないディレクトリ階層の俯瞰ツール
(`list_tree`) を追加で提供し、エージェントが構造把握から
コード調査に進む流れを支援する。

### 1.3 バックエンドコマンドの選定方針

各ツールの内部で利用する外部コマンドは、機能要件を満たすことを
前提とした上で、**速度を最も強い選定理由**とする。

エージェントは1つの応答中に複数回のツール呼び出しを行うため、
個々の呼び出しの遅延がそのままユーザー体感の遅延に直結する。
ミリ秒オーダーの差が、サーバー全体の応答性を決定する。

選定したコマンドと、その根拠となるベンチマーク数値は
「6.2 外部依存」に記載する。

## 2. スコープ

### 2.1 やること

- Git リポジトリの定期的な取得 (clone および pull)
- 指定ブランチに限定したソースコードの提供
- ファイル内容のパターン検索ツールの MCP 公開
- ファイル名パターンによる検索ツールの MCP 公開
- ディレクトリ階層を俯瞰するツールの MCP 公開
- 行範囲指定でのファイル読み取りツールの MCP 公開
- 検索結果における Git ホスティングサービス上の URL の付与
- 複数リポジトリの同時取り扱い

### 2.2 やらないこと

- ベクトル検索および埋め込みインデックスの構築
- 自然言語クエリの解釈 (これはクライアント側 LLM の責務とする)
- ソースコードの書き換え、Git への push
- ユーザーごとの権限管理 (本サーバーは単一の権限で動作する)
- チャット UI そのものの提供
- ドキュメント検索やナレッジベース検索
  (別途必要であれば別 MCP サーバーとして実装する)
- 画像、PDF、Jupyter Notebook など非テキストファイルの解釈
  (テキストとして扱える形式のみを対象とする)

## 3. 想定利用シナリオ

### 3.1 主要なシナリオ

エンドユーザーがチャットアプリに対し
「`StreamingResponseBuilder` クラスがどう実装されているか」
と問い合わせる。

クライアント側のエージェント (LLM) は本 MCP サーバーに対して
次の順序でツールを呼び出す。

1. `list_tree` でリポジトリ全体の構造を俯瞰し、関連しそうな
   ディレクトリの当たりを付ける
2. `search_code` で `StreamingResponseBuilder` を検索し、
   ヒットしたファイルパスと行番号を取得する
3. 必要に応じて `list_files` で周辺のファイル構成を確認する
4. `read_file` で該当ファイルの該当範囲を読み取り、実装内容を
   取得する

エージェントはこれらの結果を統合し、回答本文に該当ファイルの
Git URL (行番号アンカー付き) を引用として埋め込む。

### 3.2 副次的なシナリオ

- 特定のリポジトリのみを対象にした検索
- 特定のファイル拡張子に絞った検索
- 特定のクラス名・関数名を含むファイルの発見
- 初見リポジトリにおけるディレクトリ階層の俯瞰

## 4. 機能要件

### 4.1 検索ツール (search_code)

| 項目 | 内容 |
| --- | --- |
| ツール名 | `search_code` |
| 目的 | ファイル内容のパターン検索 |
| 参考仕様 | Claude Code の `Grep` ツール |
| バックエンドコマンド | `ripgrep` (`rg`) |

#### 4.1.1 入力

- `pattern` (必須): 検索パターン。正規表現として解釈する
- `repository` (必須): 検索対象のリポジトリ識別子
- `path` (任意): リポジトリ内の相対パス。省略時はリポジトリ
  全体を対象とする
- `glob` (任意): ファイル名のグロブパターン
  (例: `*.java`, `**/*.ts`)
- `type` (任意): ファイル種別ショートカット
  (例: `python`, `java`, `rust`)
- `case_sensitive` (任意): 大文字小文字を区別するか。
  デフォルトは `false`
- `output_mode` (任意): `content` (一致行を返す。デフォルト)、
  `files_with_matches` (一致したファイルパスのみ)、
  `count` (ファイルごとの一致数のみ) のいずれか
- `context_before` (任意): 一致行の前に含める行数。デフォルトは 0
- `context_after` (任意): 一致行の後に含める行数。デフォルトは 0
- `max_results` (任意): 返す最大ヒット数。デフォルトは 50、
  上限は 500

#### 4.1.2 出力

各ヒットについて以下の情報を返す。

- `repository`: リポジトリ識別子
- `file_path`: リポジトリルートからの相対パス
- `line_number`: 1 始まりの行番号
- `line_content`: ヒットした行の内容
  (`context_before` および `context_after` で指定された
  前後行を含む場合は、それらも含む)
- `git_url`: Git ホスティングサービス上の該当行への URL

#### 4.1.3 挙動

- `.gitignore` に記載されたファイルは検索対象から除外する
- バイナリファイルは検索対象から除外する
- 隠しファイル (`.` で始まるファイル) は検索対象から除外する

### 4.2 ファイル名検索ツール (list_files)

| 項目 | 内容 |
| --- | --- |
| ツール名 | `list_files` |
| 目的 | ファイル名パターンに一致するファイルを検索 |
| 参考仕様 | Claude Code の `Glob` ツール |
| バックエンドコマンド | `ripgrep --files` (`rg --files`) |

#### 4.2.1 入力

- `repository` (必須): リポジトリ識別子
- `pattern` (必須): グロブパターン
  (例: `**/*.java`, `src/**/Controller*.ts`)
- `path` (任意): リポジトリ内の検索起点となる相対パス。
  デフォルトはリポジトリルート
- `max_results` (任意): 返す最大ファイル数。デフォルトは 100、
  上限は 500

#### 4.2.2 出力

各ファイルについて以下の情報を返す。

- `repository`: リポジトリ識別子
- `file_path`: リポジトリルートからの相対パス
- `last_modified`: ファイルの最終更新時刻 (ISO 8601 形式)
- `git_url`: Git ホスティングサービス上の該当ファイルへの URL

結果は最終更新時刻の降順 (新しいものが先) で並べる。

#### 4.2.3 挙動

- `.gitignore` に記載されたファイルも結果に含める
  (Claude Code の Glob と同じ既定動作とする)
- バイナリファイルも結果に含める
- 結果が上限に達した場合は、その旨を示すフラグを応答に含める

### 4.3 ディレクトリ階層ツール (list_tree)

| 項目 | 内容 |
| --- | --- |
| ツール名 | `list_tree` |
| 目的 | リポジトリ内のディレクトリ階層を俯瞰する |
| 参考仕様 | LangChain `list_public_directory` |
| バックエンドコマンド | `git ls-files` (出力をサーバー内でツリー整形) |

#### 4.3.1 入力

- `repository` (必須): リポジトリ識別子
- `path` (任意): リポジトリルートからの相対パス。
  デフォルトはリポジトリルート
- `max_depth` (任意): 走査する最大深さ。デフォルトは 2、
  上限は 5
- `show_files` (任意): ファイルも結果に含めるか。
  デフォルトは `true`。`false` の場合はディレクトリのみを返す
- `max_entries` (任意): 返すエントリの最大数。デフォルトは 200、
  上限は 1000

#### 4.3.2 出力

- `repository`: リポジトリ識別子
- `root_path`: 走査の起点となった相対パス
- `tree`: ツリー構造のテキスト表現 (ASCII アート形式)
- `truncated`: 上限に達して結果が打ち切られたかを示すフラグ

#### 4.3.3 挙動

- 結果には Git で追跡されているファイルのみが含まれる。
  未追跡ファイル、`.gitignore` で無視されたファイルは含めない
  (`git ls-files` のデフォルト挙動に従う)
- ディレクトリ構造はバックエンドコマンドの出力 (パスのリスト)
  から、サーバー内で組み立てる
- 結果が `max_entries` を超える場合は、深さ優先でその時点までの
  内容を返し、`truncated` を `true` にする

### 4.4 ファイル読み取りツール (read_file)

| 項目 | 内容 |
| --- | --- |
| ツール名 | `read_file` |
| 目的 | 指定ファイルの内容を行番号付きで読み取る |
| 参考仕様 | Claude Code の `Read` ツール |
| バックエンドコマンド | なし (Python 標準ライブラリで実装) |

`read_file` のみ外部コマンドを使わない理由は、本ツールが
単一の小さなテキストファイルから最大 2000 行の範囲を読み取る
処理であり、外部プロセスの起動コスト (典型的に 5〜20 ミリ秒)
が読み取り処理そのもの (1 ミリ秒未満) を上回るため。
プロセス起動を挟む方が遅くなる。

`search_code` および `list_files` で外部コマンド (ripgrep) を
採用するのは、リポジトリ全体の並列走査において並列処理の利得が
プロセス起動コストを大きく上回るためであり、`read_file` には
その前提が当てはまらない。

#### 4.4.1 入力

- `repository` (必須): リポジトリ識別子
- `file_path` (必須): リポジトリルートからの相対パス
- `start_line` (任意): 開始行 (1 始まり)。デフォルトは 1
- `num_lines` (任意): 読み取る行数。デフォルトは 100、
  上限は 2000

#### 4.4.2 出力

- `repository`: リポジトリ識別子
- `file_path`: ファイルパス
- `start_line`: 実際の開始行
- `end_line`: 実際の終了行
- `total_lines`: ファイル全体の行数
- `content`: 行番号付きのファイル内容
- `git_url`: Git ホスティングサービス上の該当範囲への URL

#### 4.4.3 挙動

- テキストとして解釈できないファイル (画像、PDF、実行ファイル
  などのバイナリ) を指定された場合は、その旨を示すエラーを返す
- ファイル全体のサイズが極端に大きい場合は、`start_line` と
  `num_lines` を指定して範囲を絞るよう促すエラーを返す
  (閾値はデプロイ設定とする)

### 4.5 Git 同期

#### 4.5.1 初期取得

サーバー起動時、設定ファイルに記載された各リポジトリについて、
未取得であれば `git clone` を実行する。
取得対象は設定で指定されたブランチに限定する。

#### 4.5.2 定期更新

スケジューラにより、設定された間隔で `git fetch` および
強制リセット (`git reset --hard origin/<branch>`) を実行する。

デフォルトの更新間隔は 15 分とする。

更新間隔はリポジトリごとに上書き可能とする。

#### 4.5.3 ブランチ制約

設定ファイルで指定されたブランチのみを参照可能とする。

他ブランチへの切り替えや、参照ブランチ以外の追跡は行わない。

### 4.6 設定管理

#### 4.6.1 設定ファイル

リポジトリ定義はリポジトリ設定ファイル (例: `repos.toml`) に
記述する。各エントリは以下を含む。

- リポジトリ識別子 (一意)
- Git のリモート URL
- 参照するブランチ
- Git ホスティング種別 (URL 生成のため。GitHub、GitLab、
  Bitbucket、自前ホストなど)
- 更新間隔の上書き (任意)
- 検索除外パス (任意)

#### 4.6.2 秘密情報

認証情報 (Personal Access Token、SSH キー参照など) は設定
ファイルとは別ファイル (例: `secrets.toml`) に分離する。

秘密情報ファイルはパーミッション 600 とし、リポジトリには
コミットしない。

### 4.7 Git URL の生成

検索結果およびファイル読み取り結果には、対応する Git ホスティング
サービス上の URL を含める。URL には行番号アンカーを付与する。

| ホスティング種別 | URL 形式の例 |
| --- | --- |
| GitHub | `https://github.com/<owner>/<repo>/blob/<branch>/<path>#L<n>` |
| GitLab | `https://gitlab.com/<owner>/<repo>/-/blob/<branch>/<path>#L<n>` |
| Bitbucket | `https://bitbucket.org/<owner>/<repo>/src/<branch>/<path>#lines-<n>` |

範囲を指定する場合は、ホスティングサービスの記法に従って範囲
アンカーを生成する。

## 5. 非機能要件

### 5.1 性能

- 単一の `search_code` 呼び出しは、対象が 100 万行規模の
  リポジトリ群であっても、95 パーセンタイルで 2 秒以内に
  応答すること
- 単一の `read_file` 呼び出しは 500 ミリ秒以内に応答すること
- 単一の `list_files` 呼び出しは 1 秒以内に応答すること
- 単一の `list_tree` 呼び出しは 1 秒以内に応答すること

### 5.2 可用性

- サーバー再起動後、Git 同期処理を待たずに既存のローカル
  ワークスペースに対して即座に検索を提供できること
- 個別リポジトリの取得失敗が、他リポジトリの利用可能性に
  影響しないこと

### 5.3 信頼性

- Git 同期失敗時はログに記録し、次回スケジュール時に再試行する
- 検索ツールが失敗した場合は、原因を判別可能なエラー応答を返す
  (該当リポジトリが存在しない、パスが範囲外など)

### 5.4 セキュリティ

- ローカルワークスペース外へのパストラバーサルを禁止する
  (例: `../`、絶対パスの拒否)
- 設定で宣言されていないリポジトリへのアクセスを拒否する
- 秘密情報をログに出力しない
- 同期処理は最小権限の認証情報で行う (push 権限を要求しない)
- MCP クライアントは内部ネットワークまたは認証済み経路からの
  接続に限定する想定とする (本サーバー自体の認証機構は要件
  に含まないが、デプロイ方式で担保する)

### 5.5 リソース制約

- `read_file` の最大読み取り行数は 2000 行
- `search_code` の最大ヒット数は 500 件 (要求値が超えた場合は
  500 に丸める)
- `list_files` の最大返却ファイル数は 500 件
- `list_tree` の最大エントリ数は 1000 件、最大深さは 5
- 1 リポジトリあたりのワークスペース上限サイズはデプロイ時の
  設定とする

### 5.6 運用性

- 起動時、定期同期時、ツール呼び出し時の主要イベントを構造化
  ログとして出力する
- 各リポジトリの最終同期時刻と同期結果を確認できる手段を提供する

## 6. 制約と前提

### 6.1 実装言語と動作環境

- 実装言語は Python とする
- パッケージ管理は uv を用いる
- 動作環境は Linux または macOS とする

### 6.2 外部依存

#### 6.2.1 必須コマンド

サーバーから以下のバイナリが呼び出し可能であること。

| コマンド | 用途 | 選定理由 |
| --- | --- | --- |
| `git` | リポジトリ取得・更新、`list_tree` のファイル列挙 | 業界標準。代替なし。後述の 6.2.3 を参照 |
| `ripgrep` (`rg`) | `search_code`、`list_files` | 後述の 6.2.2 を参照 |

`read_file` は外部コマンドを使わず Python 標準ライブラリで
実装する。理由は 4.4 に記載のとおり、本ツールの処理規模では
プロセス起動コストが読み取り処理を上回るため。

#### 6.2.2 ripgrep 選定の根拠

ripgrep は内容検索 (`search_code`) とファイル列挙 (`list_files`) の
両方をカバーする。Cursor、Claude Code、Codex CLI、Aider など
主要な AI コーディングエージェントが共通して採用している
バックエンドであり、本サーバーも同じ選択を取る。

ベンチマーク (引用は本書末尾の参考文献を参照):

- Linux カーネルソース (75K ファイル, 約 900 MB): ripgrep 0.082 秒、
  GNU grep 0.671 秒 (約 8 倍)
- 10 GB モノレポでの再帰検索: ripgrep 0.6 秒、GNU grep 8.2 秒
  (約 13 倍)
- 13.5 GB 単一ファイル検索: ripgrep 1.664 秒、GNU grep 9.484 秒
  (約 5.7 倍)

高速性の根拠:

- リテラルパターン検索で CPU の SIMD ベクトル命令を活用
- 全 CPU コアでのワークスティーリング並列ディレクトリ走査
- `.gitignore` および隠しファイルを開く前に除外
- バイナリファイルの自動除外

`list_files` で `rg --files -g <glob>` を使うことで、
`fd` などの別バイナリを追加せずにファイル列挙を実現する
(`fd` と `ripgrep` は同じ Rust 製 `ignore` クレートを共有しており、
ファイル列挙の速度は事実上同等である)。

候補比較の結果:

| 候補 | 内容検索 | ファイル列挙 | 速度 | 採用判断 |
| --- | --- | --- | --- | --- |
| `ripgrep` | 可 | 可 (`--files`) | 最速級 | **採用** |
| `GNU grep` | 可 | 不可 | ripgrep の 1/5〜1/13 | 不採用 |
| `ag` | 可 | 不可 | ripgrep より遅い、開発停止 | 不採用 |
| `git grep` | 可 | 不可 | git 文脈に限定 | 不採用 |
| `fd` | 不可 | 可 | ripgrep --files と同等 | 不採用 (依存追加価値なし) |

##### 6.2.2.1 規模制約

100 万ファイルを超える巨大モノレポでは ripgrep でも 15 秒以上を
要する場合がある。本サーバーは 6.4 の規模前提
(1 リポジトリ 5 GB 以下) に収まる範囲を想定する。

#### 6.2.3 git ls-files 選定の根拠

`list_tree` のファイル列挙には `git ls-files` を用い、
ツリー整形はサーバー内で行う。

選定理由:

- `git` は同期処理で既に必須のため、依存が追加されない
- `.gitignore` および追跡対象の判定は git 本体に任せられ、
  最も正確に動作する
- 未追跡ファイルが結果に出現しないため、誤って機密ファイル
  (環境設定、ローカルメモなど) を露出させるリスクが低い
- 出力は単純なパス一覧であり、ツリー整形ロジックを差し替える
  際の前段としても扱いやすい

`list_tree` は深さ制限付きの俯瞰用途であり、`eza --tree` のような
リッチなツリー描画機能は不要である。サーバー側で `max_depth` と
`max_entries` を適用しながら整形すれば、エージェントが消費する
出力サイズも制御しやすい。

候補比較の結果:

| 候補 | `.gitignore` 尊重 | 依存追加 | 整形 | 採用判断 |
| --- | --- | --- | --- | --- |
| `git ls-files` + サーバー整形 | 完全 | なし | サーバー | **採用** |
| `eza --tree --git-ignore` | 可 | あり | 外部に任せられる | 不採用 (依存追加価値が薄い) |
| `tree` (古典) | 不可 | あり | 外部に任せられる | 不採用 |
| `broot` | 可 | あり | 対話 TUI | 不採用 (非対話用途に不向き) |

##### 6.2.3.1 起動コストに関する注意

`list_tree` の処理量は他ツールに比べて小さいため、`git ls-files`
プロセスの起動コスト (典型的に 5〜20 ミリ秒) が全体処理時間に
占める割合が相対的に大きい。それでも 5.1 性能要件
(1 秒以内) に対しては十分な余裕があり、許容範囲とする。

将来、起動コストがボトルネックになった場合は、Python の
`pygit2` 等のライブラリ呼び出しに切り替える余地がある。

#### 6.2.4 ネットワーク

ネットワーク経由で Git リモートに到達可能であること。

### 6.3 MCP トランスポート

- 標準入出力 (stdio) と HTTP/SSE の両方をサポートする
- どちらを使うかは起動時に選択可能とする

### 6.4 リポジトリ規模の前提

- 1 サーバーインスタンスが扱うリポジトリ数は 50 以下を想定する
  (= 性能・ディスクの物理上限)
- 1 リポジトリあたりのサイズは 5 GB 以下を想定する

#### 6.4.1 LLM 文脈の都合による実運用上限

物理上限とは別に、**MCP クライアントが LLM に渡せるコンテキスト枠は
実質 1% スケール (数千 tokens)** に過ぎないため、1 サーバインスタンス
あたりの **実運用上のリポジトリ数は 5〜10 程度** が現実的である。

`list_repositories` の応答や `resources/list` の各 description が
LLM 文脈に乗ることで、リポ数が増えるほどトークン消費が線形に増える。
50 リポ × 各 description 200 トークンで既に 10K トークンに達する。

50 リポを超える運用では、以下のいずれかを取ること:

- チーム / ドメイン単位で MCP サーバインスタンスを **分割** し、
  各クライアントが用途に応じて接続先を切り替える
- リポジトリ description を空にしてカタログを軽くする
  (LLM のリポ選択精度を犠牲にする)

### 6.5 公開ツールの方針

- MCP サーバーが公開する検索系ツールは `search_code`、`list_files`、
  `list_tree`、`read_file` の 4 つに限定する。これに加え、リポジトリ
  カタログを LLM に届けるための discovery ツール `list_repositories` を
  1 つ公開する (Resources を文脈に注入しない MCP ホストへの対策)
- ツール名・パラメータ名は小文字スネークケースとする
- 自然言語応答や要約は本サーバーの責務としない

## 7. 用語定義

| 用語 | 定義 |
| --- | --- |
| MCP | Model Context Protocol。LLM クライアントが外部ツールに アクセスするためのプロトコル |
| MCP サーバー | MCP プロトコルでツールを公開するサーバー |
| MCP クライアント | MCP サーバーのツールを利用するクライアント (通常は LLM を内包するチャットアプリ) |
| ツール | MCP プロトコルで公開される呼び出し可能な関数 |
| リポジトリ | 本サーバーで取り扱う単一の Git リポジトリ |
| 参照ブランチ | リポジトリごとに設定で指定された、検索対象となるブランチ |
| ワークスペース | 各リポジトリの clone 先となるサーバー上のローカル ディレクトリ |
| ヒット | `search_code` で返される単一の一致箇所 |
